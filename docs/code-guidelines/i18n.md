# Internacionalización

Regla 24 del `CLAUDE.md` raíz. **Obligatoria, no opcional, desde el primer componente.**

## La regla

Ningún texto que vea un usuario se escribe literal en un `.html`, `.ts` o `.dart`.
Todo pasa por la capa de traducción con su clave.

Idiomas desde el inicio: **inglés (`en`) y español (`es`)**. El `locale` es por
usuario, no por empresa: William administra en inglés y es probable que sus
trabajadores usen el móvil en español, dentro de la misma cuenta.

## Qué cuenta como texto de usuario

Todo esto, sin excepciones:

- Labels, botones, títulos, placeholders
- Mensajes de error y de validación
- Estados vacíos y textos de carga
- Tooltips y textos de ayuda
- Confirmaciones y diálogos
- **El texto de las notificaciones push** — se traduce con el locale del
  destinatario, no con el de quien dispara la acción
- **Los PDF de estimados y facturas** — el cliente final puede leer en otro idioma
  que el contratista

Lo que **no** se traduce: nombres propios, códigos, identificadores, y los datos
que carga el usuario.

## Nomenclatura de claves

Jerárquica, por frente y pantalla. Nunca por el texto en inglés.

```
projects.list.title
projects.list.empty
projects.form.name.label
projects.form.name.error.required

timeEntry.clockIn.button
timeEntry.clockIn.error.noGps
timeEntry.flag.outsideGeofence

invoices.status.overdue
common.actions.save
common.actions.cancel
```

```json
// ❌ la clave es el texto: si cambia el copy, cambia la clave en 40 archivos
{ "Save": "Guardar" }

// ✅
{ "common.actions.save": "Guardar" }
```

## Nunca concatenar

Es el bug clásico de i18n y no se ve hasta que se traduce.

```ts
// ❌ el orden de las palabras cambia entre idiomas
`${count} fotos subidas a ${projectName}`

// ✅ interpolación con parámetros
t('photos.uploaded', { count, projectName })
```

```json
{
  "photos.uploaded": "{{count}} photos uploaded to {{projectName}}",
  "photos.uploaded_one": "1 photo uploaded to {{projectName}}"
}
```

Los plurales van por la API de pluralización de la librería, no con un `if`.
Español e inglés tienen dos formas; otros idiomas tienen más, y un `if` no escala.

## Fechas, moneda y números

Se formatean por la capa de i18n. **Nunca concatenando.**

```ts
// ❌
`$${(cents / 100).toFixed(2)}`
`${date.getMonth() + 1}/${date.getDate()}`

// ✅
formatCurrency(cents, locale, currency)   // Intl.NumberFormat
formatDate(date, locale, timeZone)        // Intl.DateTimeFormat
```

`$` pegado a un número es un bug esperando al primer cliente que no facture en
dólares. Y el formato de fecha `MM/DD` contra `DD/MM` es una confusión garantizada
entre un usuario en Maryland y uno en Costa Rica.

**La zona horaria va explícita**, siempre la de la empresa (`America/New_York`).
Nunca la del navegador: un timesheet que se ve distinto según dónde esté parado
quien lo abre no sirve como evidencia.

## Angular — decisión pendiente de ADR

Hay un hallazgo que condiciona la elección y conviene tenerlo escrito:

> El `$localize` nativo de Angular procesa cada mensaje **una sola vez**, cuando
> se encuentra por primera vez. `loadTranslations()` en runtime no cambia lo ya
> traducido. La documentación oficial lo dice explícitamente: **no soporta cambio
> dinámico de idioma sin recargar el navegador.**

Eso deja dos caminos:

| Opción | Cómo funciona | Costo |
|---|---|---|
| **`@angular/localize` nativo** | Un build por idioma (`ng build --localize`), se sirve `/en/` y `/es/`. Traducción inlineada en compilación. | Cambiar de idioma = recargar o redirigir. Formato XLIFF, distinto del de Flutter. |
| **Transloco** | Catálogos JSON cargados en runtime, cambio de idioma sin recargar, un solo build. | Una dependencia más; las traducciones viajan al cliente. |

**Recomendación: Transloco**, por dos razones concretas de este proyecto — los
catálogos JSON se comparten con Flutter y con el sitio en Astro sin convertir
formatos, y el cambio de idioma sin recargar importa porque el `locale` es por
usuario dentro de una misma cuenta.

No está decidido. **Va a ADR antes del primer componente**, porque migrar de una
a otra con la app llena de claves es caro.

## Flutter

`flutter_localizations` con archivos ARB y `gen-l10n` — es el estándar y soporta
cambio de idioma en runtime sin problema.

```dart
// ❌
Text('Clock in')

// ✅
Text(AppLocalizations.of(context)!.clockIn)
```

Los ARB son JSON con metadata, así que los catálogos se mantienen alineados con
los de la web sin traducir dos veces.

## Qué dice el texto, no solo en qué idioma está

Traducir bien no alcanza si la frase está escrita desde el sistema. Tres reglas
que salieron de corregir el mismo error varias veces en el frente de fotos.

**Decir lo que va a ser cierto, no lo que deja de pasar.** El sistema piensa en
transiciones —algo se quita, algo se deja de ver—; la persona piensa en estados.

| ❌ Desde el sistema | ✅ Desde quien lo lee |
|---|---|
| "Deja de verse fuera de la empresa." | "Esta foto solo la verá el equipo." |
| "Se borra de este teléfono y del servidor." | "Esta foto no se va a poder recuperar." |
| "Sale en la página web y en las redes." | "Esta foto la verá cualquiera en la página web." |

**Nombrar al sujeto.** "La verá en el portal" no dice quién. El cliente, el
equipo, cualquiera: si la frase habla de quién ve algo, ese quién va escrito.

**No explicar la mecánica.** "La visibilidad sube de a un nivel" describe cómo
está hecho el producto, no qué hacer. Si la escalera nunca ofrece un salto, no
hay nada que prevenir; si el servidor lo rechaza, el mensaje dice el próximo
paso —"Primero hay que mostrársela al cliente"—, no la regla.

El porqué del producto vive en el spec. Un párrafo de ayuda en pantalla dice
para qué sirve lo que se está tocando, y nada más.

## Qué revisar antes de aprobar

- [ ] ¿Hay alguna cadena entre comillas que vaya a ver un usuario?
- [ ] ¿Las claves son jerárquicas y no el texto en inglés?
- [ ] ¿Hay alguna concatenación de texto traducido?
- [ ] ¿Los plurales usan la API de pluralización?
- [ ] ¿Fechas y montos pasan por el formateador, con zona horaria explícita?
- [ ] ¿Existen las dos traducciones, `en` y `es`?
- [ ] ¿Cada frase dice lo que va a ser cierto, con su sujeto, sin explicar la
      mecánica del sistema?

Una clave sin traducir en un idioma debe **fallar visiblemente** en desarrollo
(mostrar la clave cruda), no caer en silencio al idioma por defecto. Un fallback
silencioso significa que la app se publica a medio traducir sin que nadie lo note.
